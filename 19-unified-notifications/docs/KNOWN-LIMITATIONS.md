# Known Limitations

These are external acceptance dependencies, not hidden File 19 repository omissions:

- File 00 canonical assertions, File 02 fresh passkey assurance, File 20 notification-surface/Safe Mode signals, File 24 containment and File 26 saved-search ownership require their exact companion runtime versions; repository companion PRs do not establish deployed parity.
- File 25 remains the visual-token/component owner; File 19 keeps scoped accessible fallbacks but cannot prove final integrated styling without the owner runtime.
- Push, SMS, FCM, APNs, WhatsApp and RCS transmission require configured approved providers. Provider acceptance is not proof of handset/carrier delivery.
- Email delivery depends on WordPress/SMTP configuration; provider acceptance is not proof of inbox delivery.
- Domain notification facts require real owner producers. File 19 does not fabricate File 08 clinic, File 17 communication, File 21 publishing/social, analytics, media or other domain truth when an owner implementation is missing or not integrated.
- WordPress `WP-Cron` timing is best-effort; production should use a reliable server cron trigger.
- Legacy migration is **not assumed unnecessary** merely because no adapter is registered. It becomes not-applicable only when an owner contract explicitly attests that no legacy notification source remains; otherwise current inventory/dry-run/rollback evidence is required.
- Full browser, screen-reader, RTL/localization, load, penetration, provider, backup/restore, rollback, Hostinger staging and Live parity cannot be proven by repository-only tests.
- Repository/CI completion never implies **Staging-Accepted**, **Live-Deployed** or **Operational**.
